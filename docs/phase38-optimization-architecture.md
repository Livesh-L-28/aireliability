# Phase 38: Multi-Objective AI Reliability Optimization Architecture

This document specifies the architecture, data models, search strategies, Pareto frontier computation, safety gates, and integration bridges of the **AI Reliability Optimization Engine** (`aireliability.optimization`).

---

## 1. System Overview & Objective

Building production AI systems requires navigating complex trade-offs between competing objectives:
- **Quality & Faithfulness** vs. **Latency**
- **Safety & Security** vs. **Permissiveness**
- **Groundedness & Recall** vs. **Token Usage & FinOps Cost**
- **Robustness** vs. **Throughput**

Standard optimization engines collapse multi-dimensional objectives into a single naive weighted sum or aggressively minimize cost at the expense of reliability. The **AI Reliability Optimization Engine** enforces the fundamental principle:

> **OPTIMIZATION MUST NEVER BYPASS RELIABILITY.**
> A configuration that is cheaper or faster but introduces safety degradations, security vulnerabilities, or critical regressions is immediately vetoed.

## 2. End-to-End Lifecycle Architecture

The optimization engine executes an immutable, auditable 13-stage lifecycle:

## 3. Optimization Problem Model

All domain models are strongly typed Pydantic models in [`src/aireliability/optimization/models.py`](../src/aireliability/optimization/models.py):

### Key Entities
- **`OptimizationObjective`**: Defines ID, target metric, direction (`MAXIMIZE`, `MINIMIZE`, `TARGET`), weight, thresholds, and safety classification.
- **`OptimizationConstraint`**: Defines metric, operator (`<=`, `>=`, `==`, `<`, `>`), threshold value, and whether it is a `hard` veto constraint.
- **`OptimizationVariable`**: Explicitly registered parameter with type (`FLOAT`, `INT`, `STRING`, `BOOLEAN`, `CATEGORICAL`), domain range `[min, max]`, step size, allowed choices, and component category.
- **`OptimizationConfiguration`**: Key-value mapping of parameter values with deterministic fingerprinting.
- **`OptimizationCandidate`**: Specific configuration generated by a search strategy with status (`PENDING`, `EVALUATING`, `EVALUATED`, `DOMINATED`, `PARETO_OPTIMAL`, `INVALID`, `SELECTED`, `REJECTED`).
- **`ParetoPoint` & `ParetoFrontier`**: Represents non-dominated points in multi-dimensional objective space with crowding distance.
- **`OptimizationBudget`**: Enforces strict execution limits (`max_candidates`, `max_evaluations`, `max_runtime_seconds`, `max_cost_usd`, `max_tokens`).
- **`OptimizationPolicy`**: Enforces organizational rules (`auto_select`, `auto_deploy`, `canary_required`, `selection_strategy`, `allowed_risk`).
- **`OptimizationResult`**: Complete immutable audit record with baseline comparison, Pareto frontier, selected candidate, and stopping reason.

## 4. Deterministic Configuration Fingerprinting

To guarantee caching efficiency, deduplication, and auditable traceability, every configuration receives a deterministic SHA-256 fingerprint:
- Volatile keys (`id`, `timestamp`, `created_at`, `execution_time`, `metadata`, `provenance`) are stripped recursively.
- Nested structures and keys are sorted alphabetically.
- Floats are rounded to 6 decimal places to eliminate floating-point precision jitter.
- The normalized dictionary is converted to UTF-8 JSON and hashed with SHA-256.

Equivalent configurations produce identical fingerprints regardless of generation path or environment.

## 5. Registered Variables & Security Isolation

Optimization inputs are treated as untrusted. Arbitrary keys, shell commands, code execution, and unverified model downloads are strictly forbidden.

### Supported Component Categories & Registered Variables

| Category | Registered Variables | Type | Domain / Constraints |
|---|---|---|---|
| **MODEL** | `model_name`, `model_version` | String / Categorical | Registered model identifiers only |
| **GENERATION** | `temperature`, `max_tokens`, `top_p`, `frequency_penalty`, `presence_penalty` | Float / Int | Strict numeric bounds (e.g. temp: 0.0–2.0) |
| **RETRIEVAL** | `top_k`, `similarity_threshold`, `reranker_threshold`, `hybrid_alpha`, `context_window` | Int / Float | Bounded search & threshold ranges |
| **RAG** | `chunk_count`, `context_size`, `context_ordering`, `enable_reranking` | Int / String / Bool | Explicit bounded limits |
| **PROMPT** | `prompt_version`, `prompt_template`, `instruction_variant` | String / Categorical | Registered template aliases |
| **TOOL** | `timeout`, `retry_count`, `concurrency`, `fallback_strategy` | Int / Float / String | Operational limits |
| **AGENT** | `max_steps`, `retry_limit`, `tool_choice_mode`, `replanning_strategy` | Int / String | Trajectory safety limits |
| **INFRASTRUCTURE**| `batch_size`, `concurrency_limit`, `request_timeout` | Int / Float | Resource limits |

Input validation rejects any unregistered variable, negative timeouts, out-of-bounds parameters, and attempts to pass executable commands.

## 6. Deterministic Search Strategies

Six pluggable search strategies implement the `BaseSearchStrategy` protocol:

1. **Grid Search (`GridSearchStrategy`)**:
   - Exhaustive Cartesian product of bounded parameter grids.
   - Enforces `max_combinations` and `max_candidates` caps to prevent combinatorial explosions.
2. **Random Search (`RandomSearchStrategy`)**:
   - Deterministic pseudo-random generation initialized via `seed`.
   - Generates candidates within valid domains, discarding duplicates via fingerprints.
3. **Local Search (`LocalSearchStrategy`)**:
   - Explores 1-hop and 2-hop perturbations from the baseline configuration.
   - Incrementally shifts continuous variables by `step` and selects adjacent categorical choices.
4. **Hill Climbing (`HillClimbingStrategy`)**:
   - Evaluates neighbor configurations and advances greedily toward configurations with higher surrogate objective improvements.
   - Terminates upon convergence, local maxima, or budget exhaustion.
5. **Bayesian-Style Optimization (`BayesianOptimizationStrategy`)**:
   - Lightweight, dependency-free surrogate model using Inverse Distance Weighting (IDW) mean estimation and uncertainty-aware Upper Confidence Bound (UCB):
     $$\text{Acquisition}(x) = \hat{\mu}(x) + \kappa \cdot \hat{\sigma}(x)$$
   - Guides exploration toward promising unexplored regions without requiring external heavy ML dependencies.
6. **Bounded Evolutionary Search (`EvolutionarySearchStrategy`)**:
   - Genetic algorithm maintaining a fixed population size.
   - Employs tournament selection, uniform crossover, bounded Gaussian/step mutation, and elitism to preserve best candidates.

## 7. Multi-Objective Optimization & Pareto Dominance

### Pareto Dominance Definition
Given candidate configurations $A$ and $B$, $A$ **dominates** $B$ ($A \succ B$) if and only if:
1. $A$ is no worse than $B$ across all objectives:
   $$\forall i, \quad f_i(A) \ge f_i(B) \text{ (for maximization)}$$
2. $A$ is strictly better than $B$ in at least one objective:
   $$\exists j, \quad f_j(A) > f_j(B)$$

### Non-Dominated Sorting & Crowding Distance
- **Pareto Frontier**: The set of all feasible candidates that are not dominated by any other feasible candidate.
- **Crowding Distance (NSGA-II)**: Quantifies candidate diversity along the frontier. Candidates in sparse regions receive higher crowding distance, preventing premature clustering around a single trade-off mode.
- **Normalization**: Objective values are normalized to $[0, 1]$ before computing diversity and distance metrics.

## 8. Hard Constraints & Reliability Gates

### Pre-Pareto Hard Veto
Hard constraints are evaluated **prior to** Pareto dominance calculations:
- Any candidate violating a hard constraint (`safety_score < threshold`, `security_violations > 0`, `critical_regressions > 0`) is marked `INVALID`.
- An invalid candidate **never** enters the Pareto frontier, regardless of exceptional cost or latency scores.

### No-Feasible-Solution Handling
If all generated candidates violate hard constraints:
- The engine halts with `StoppingReason.NO_FEASIBLE_CONFIGURATION`.
- The engine returns an audit report detailing every constraint violation without arbitrarily selecting a compromised candidate.

### Post-Selection Reliability Gates
Even if a candidate is Pareto-optimal, it must pass `OptimizationGateChecker`:
- Zero critical regressions compared to baseline.
- Minimum quality threshold ($\ge 0.80$).
- Minimum safety threshold ($\ge 0.95$).
- Minimum security threshold ($\ge 0.95$).

## 9. Evaluation Loop, Confidence, and Caching

### Repeated Candidate Evaluation
When `repeated_evaluations > 1`, candidates are evaluated repeatedly to calculate:
- Mean and Median metric values
- Variance and Standard Deviation
- Statistical Confidence Score:
  $$\text{Confidence} = \min\left(1.0, \frac{N}{10}\right) \times (1.0 - \min(1.0, \text{variance}))$$

### Multi-Tier Result Caching
Evaluation results are cached using a composite key:
$$\text{CacheKey} = \text{hash}(\text{candidate\_fingerprint} + \text{dataset\_id} + \text{model\_version} + \text{evaluator\_version})$$
Cached results prevent redundant evaluations while automatically invalidating if datasets, models, or evaluator versions change.

## 10. Policy-Driven Configuration Selection

Selecting a final candidate from the Pareto frontier is governed by `OptimizationPolicy`:

- `BALANCED_SCORE`: Selects the candidate with the highest normalized Euclidean distance from the worst frontier anchor.
- `HIGHEST_QUALITY`: Selects the Pareto candidate maximizing quality metrics.
- `LOWEST_COST`: Selects the Pareto candidate minimizing FinOps cost.
- `LOWEST_LATENCY`: Selects the Pareto candidate minimizing latency.
- `WEIGHTED_PREFERENCE`: Applies user-specified objective weights to rank frontier candidates.

### Deterministic Tie-Breaking Hierarchy
When multiple candidates have identical utility scores, ties are resolved deterministically using the following strict hierarchy:
1. Higher Safety Score
2. Higher Security Score
3. Higher Reliability Score
4. Lower Error Rate
5. Lower Cost
6. Lower Latency

## 11. Cross-Phase Integrations

### Phase 36: Test Generation Integration (`OptimizationTestBridge`)
When an optimization candidate alters critical variables (such as retrieval thresholds or prompt templates), the test bridge invokes Phase 36's `TestGenerationEngine` to synthesize targeted edge-case and robustness tests, adding them to the validation suite.

### Phase 37: Self-Healing & Safe Rollout Integration (`OptimizationDeploymentBridge`)
The optimization engine does **not** deploy configurations directly:
1. Selected candidate is packaged into a Phase 37 `RemediationProposal`.
2. Evaluated against `HealingPolicy` and submitted for operator approval via `ApprovalManager`.
3. Deployed progressively via `RolloutController` (`SHADOW` or `CANARY`).
4. Monitored in real-time by `RemediationVerifier`.
5. Promoted to 100% production baseline by `PromotionManager` if healthy, or immediately reverted by `RollbackManager` upon degradation.

### Phase 35: Knowledge Graph Integration (`OptimizationGraphBridge`)
Optimization runs, baseline nodes, candidate nodes, and evaluation metrics are synchronized into the Phase 35 `KnowledgeGraph`:
- Nodes: `EXPERIMENT` (run), `BASELINE` (reference), `METRIC` (achieved values).
- Edges: `EVALUATED`, `PRODUCED`, `COMPARED_WITH`, `IMPROVES`, `VIOLATES`, `SELECTED`.
- Lineage queries support historical retrieval of prior Pareto frontiers to guide future optimization candidate ordering.

### Phase 22: Production Observability (`OptimizationObservabilityBridge`)
Emits Prometheus-compatible metrics and distributed trace spans:
- `optimization_runs_total`
- `optimization_candidates_total`
- `optimization_evaluations_total`
- `optimization_pareto_size`
- `optimization_success_total`
- `optimization_failed_total`

## 12. CLI Commands & Workflow

The `airel optimize` suite provides complete terminal workflows:

```bash
# 1. Plan optimization problem
airel optimize plan --objective "quality:maximize" --objective "latency:minimize" --variable "temperature:float:0.0:1.0:0.1" -o problem.json

# 2. Run multi-objective optimization
airel optimize run problem.json --strategy grid --max-candidates 20 --output result.json

# 3. Inspect Pareto frontier
airel optimize pareto result.json

# 4. Compare baseline with candidates
airel optimize compare result.json

# 5. Select candidate using policy
airel optimize select result.json --strategy balanced_score

# 6. Validate candidate against release gates
airel optimize validate result.json

# 7. Deploy via Phase 37 canary rollout
airel optimize deploy result.json --strategy canary --percentage 10

# 8. Rollback if degradation detected
airel optimize rollback result.json --reason "Unacceptable latency spike"

# 9. Query optimization history and budget
airel optimize history
airel optimize budget result.json
```
